## Implemented behavior

Large `ARKEM-PROJECT-SHELL-CALCULATION-RECORD/1.0` records are stored in IndexedDB `arkem-project-shell-calculations-v1`, separately from the existing localStorage project envelope. Each entry uses `ARKEM-PROJECT-SHELL-STORAGE/1.0` and retains the complete calculation JSON, including all five load cases, raw nodal/Gauss results, formulation, diagnostics and canonical prepared project source. A record is limited to 32 MiB of UTF-8 JSON. The maximum supported 2145-node / 2048-element example produced a 17,089,252-byte record; its project settings remained approximately 38 KB.

The storage key binds project ID, revision, persistent plate ID and the SHA-256 of the canonical validated source declaration. Reference ordering is canonical. Different plates, changed geometry/material/load/support/mesh/provenance or project context cannot silently select an earlier source's result. Old entries may remain as historical local data; they are not automatically migrated or attached to a different source.

Before display, restoration validates the bounded storage envelope and record identity, then calls `verifyProjectShellCalculation` in a disposable worker. That verification hashes the complete sealed content and recomputes the current declared source with the recorded formulation parameter. A matching hash alone is insufficient: rehashed fabricated results are rejected. An unsupported database version is refused without destructive migration. The stored timestamp is a device save time, not an engineering approval time.

Writes commit in an IndexedDB transaction. Quota failures, explicit aborts and failed transactions preserve the previous committed entry. A per-project deletion epoch is captured before calculation and checked in the same transaction as a write, preventing a previously opened session from resurrecting a deleted record. Concurrent connections commit complete entries. Project-specific deletion preserves other projects' entries.

The calculation panel automatically attempts restoration when its validated source mounts. It shows a record only after worker verification; source changes/unmount and cancellation stop an active worker and pending write. A new valid calculation remains available in the session if storage is unavailable, with an explicit unsaved/error message. Successful save dates are shown only after transaction completion. Raw results are not added to localStorage or automatically transferred to a frame calculation.

The project centre's local-delete action and account deletion flow await calculation cleanup before claiming local deletion success. A failed cleanup retains the active working project and reports the failure. If the active project changes while cleanup is pending, the new project's working copy is preserved. The large storage module is loaded on demand for deletion.
